# 사내망 배포 절차

사내망은 **폐쇄망(RHEL 9.4 · podman, compose 없음)** 이고, 인트라넷 업로드 필터가 **`.txt` 만**
통과시킨다. 그래서 이미지를 base64 `.txt` 로 싸서 옮긴다 — 이 문서는 그 순서다.

강원 직할은 **선번장 자료 그대로**다(`backend/src/seed/jikhalGangwon*.ts`) — 국 이름에 종별
꼬리를 붙였고(S/S·H/P·S/Y), OFD 의 광선로 끝은 **실제로 이은 슬롯만** 세운다(어댑터 시작 번호 =
엑셀 첫 No.). 직할 밖으로 나가는 슬롯(홍천S/S·강원D/D·B/O 접속함체 등)은 상대가 없어 세우지 않는다.

이것도 **첫 배포(빈 DB)에만** 만든다 — 국은 현장이 고치는 운영 데이터라, 재시작마다
덮으면 현장이 짠 구성이 원본으로 되돌아간다.

## 1. 빌드 머신에서 (인터넷 되는 곳)

```bash
git pull                       # 배포할 커밋인지 확인
npm run build                  # 타입체크 + 빌드가 통과하는지 먼저
scripts/build-prod-images.sh   # linux/amd64 로 빌드 → dist-deploy/*.txt 5개
```

나오는 것: `postgres.txt` · `backend.txt` · `frontend.txt` · `env.txt` · `deploy.txt`
(합계 수백 MB — 인트라넷 업로드 한도를 넘으면 `backend.txt` 만 나눠 올리는 식으로 쪼갠다.)

**로컬에서 먼저 검증**하는 것을 권한다. 개발 스택과 이름·볼륨이 겹치지 않는 오버라이드가 있다:

```bash
docker compose -f docker-compose.yml -f docker-compose.verify.yml build
docker compose -f docker-compose.yml -f docker-compose.verify.yml up -d
open http://twin.local:8080          # /etc/hosts 에 `127.0.0.1 twin.local`
docker compose -f docker-compose.yml -f docker-compose.verify.yml down -v
```

`localhost` 로 검증하면 안 된다 — HSTS·CSP·CORS·**보안 컨텍스트**가 운영과 달라 헛검증이 된다.
실제로 이 검증에서만 드러난 배포 차단 버그가 있었다(평문 주소에서 `crypto.randomUUID` 없음).

## 2. 서버로 옮기고 첫 실행

```bash
# 다섯 개 .txt 를 한 디렉터리에 둔 뒤
base64 -d deploy.txt > decode-and-deploy.sh
chmod +x decode-and-deploy.sh
./decode-and-deploy.sh          # 첫 실행: .env 를 만들고 멈춘다

vi .env
#   DB_PASSWORD / JWT_ACCESS_SECRET / JWT_REFRESH_SECRET  ← openssl rand -hex 32
#   CORS_ORIGIN=http://<브라우저에 치는 주소>:8080          ← 포트까지 정확히
#   DB_NAME=digital_next   FRONTEND_PORT=8080             ← 그대로 둔다
```

## 3. 옛 볼륨 비우기 (첫 배포에서 한 번만 — 이미 지났다)

```bash
podman rm -f ict-twin-postgres ict-twin-backend 2>/dev/null || true
podman volume rm postgres_data uploads_data 2>/dev/null || true
```

사진 파일은 `uploads_data` 에 있고 그 **경로는 DB 에 있다** — 한쪽만 지우면 깨진 사진이 남는다.
지우기 전에 되돌릴 길을 만들어 둔다:

```bash
podman exec ict-twin-postgres pg_dump -U postgres -d digital_next > backup-$(date +%F).sql
```

## 4. 띄우기

```bash
./decode-and-deploy.sh
podman ps
podman logs --tail=30 ict-twin-backend
```

빈 DB 에서는 아래 네 줄이 보이면 성공이다(숫자는 시드 자료에 따라 조금 다를 수 있다):

```
[seed:next] admin user created
[seed:next] org created — 본부 15
[seed:jikhal] 국 12, 광선로 13, 측정 195, 코어 값 …, 설비 …, 연결 …
{"event":"server.start","port":3000,"env":"production"}
```

데이터가 있는 DB 에서는 `admin already exists — skip` · `org already exists — skip` ·
`[seed:jikhal] 변전소가 이미 있음 — skip` 이 정상이다(7-4).

## 5. 사람이 넣는 것

1. `http://<주소>:8080` 접속 → `admin` / `admin123` → **비밀번호를 바로 바꾼다**
2. 「기준정보」 → 노임단가(hwp) · 제비율(xlsx) 업로드
3. 조직 트리에서 본부 › 사업소에 손을 올리고 `＋` → **변전소** 만들기
4. 없는 전력지사도 같은 방법으로 더한다(시드는 한전 공식 목록의 전력지사만 담았다)

## 6. 스모크 체크 (5분)

- 로그인 → 상단 메뉴가 **설비 현황 · 품목 관리 · 기준정보**, 조직 트리에 본부 15개
- **현황** — 강원본부 › 직할 › 북춘천S/S → 품목별 대수가 보이고, 「랙별」로 바꾸면 랙 → 설비(이름 자연 순서)
- **선번장** — 같은 국 → OFD 블록마다 코어 1..N, 회선 내역·상태가 보이고 상대국 이름이 블록 머리에 선다.
  코어의 「중계경로」 단추가 사슬을 연다
- **전원 계통** — 차단기 대장과 계통도가 각각 뜬다((구)춘천S/S 에 차단기·부하가 있다)
- **광 계통도** — 지사(직할)나 본부를 고르면 「현황 · 광 계통도」 탭 → 국 사이 광선로가 그려지고 오른쪽에 회선 목록
- **변경 → 설계서** — 국 하나에 「랙 추가」(같은 이름 설비 함께) → 저장 바에 변경 수 → 저장 바의 「설계서」 → 산출 내역에 그 랙·설비가 뜬다
  (노임단가를 올린 뒤라면 원가계산서까지). 시험 변경이면 「변경 취소」로 버리고, 남길 것이면 **저장**
- 기준정보에 직종 노임이 보이는지
- 브라우저 콘솔에 빨간 오류가 없는지

## 2026-10 설비 모델 단순화 배포 — **DB 리셋 필수(1회)**

포트·설비 품목(조립) 모델을 걷고 랙·설비·차단기(모델 이름 circuit)·광선로·코어·연결 모델로 바꿨다. 마이그레이션 기준선이
새로 시작하므로(`20261006000000_init`) **기존 DB 를 이어 쓸 수 없다**.
근거: **2026-10-06 제품 담당자 확인 — 현장 입력 데이터 없음, 재시드 허용.**
(이 릴리스 한 번만 아래 7 절의 「볼륨을 비우지 않는다」를 대신한다.)

**마이그레이션**은 기준선 둘뿐이다 — `backend/prisma/next/migrations` 에 **정확히 이 둘만** 있어야 한다
(빌드 머신의 작업 사본에 옛 마이그레이션 디렉터리가 남아 있으면 이미지에 실려 기준선보다 먼저 돈다 — 빌드 전에 `ls` 로 확인):

| 마이그레이션 | 무엇 |
|---|---|
| `20261006000000_init` | 새 기준선 — 랙·설비·차단기·광선로·코어·측정·연결·변경 기록 + 조직·품목·기록·사진·기준정보 |
| `20261007000000_core_end_values` | 코어 회선 내역·비고를 끝별로(`Core.purpose/note` → `aPurpose/aNote`, `bPurpose/bNote` 추가) |

**재시드는 빈 DB 의 첫 기동이 한다**(fresh) — 아래 3 단계로 볼륨을 비우면 컨테이너가 `migrate deploy` → `seed` 를
돌려 관리자·조직·마스터 품목·직할 12국을 새로 싣는다. 따로 돌릴 시드나 백필 스크립트는 없다.

1. 사전 확인: 옛 테이블에 현장 입력이 정말 없는지 센다(아래 표 이름은 **옛 스키마**의 것이다 — 지울 DB 에 대고 센다). **정비·점검·사진은 시드가 한 줄도 만들지
   않으므로 셋 다 0 이어야 한다.** 하나라도 0 이 아니면 **여기서 멈추고** 담당자에게 알린다.
   ```bash
   podman exec ict-twin-postgres psql -U postgres -d digital_next -c '
     SELECT (SELECT count(*) FROM "MaintenanceLog") AS maintenance,
            (SELECT count(*) FROM "InspectionLog")  AS inspection,
            (SELECT count(*) FROM "AssetPhoto")     AS photo,
            (SELECT count(*) FROM "Asset")          AS asset,
            (SELECT count(*) FROM "Cable")          AS cable;'
   ```
   `maintenance`·`inspection`·`photo` 는 반드시 0. `asset`·`cable` 은 직할 시드가 만든 수만큼 있다 —
   담당자에게 그 두 수를 함께 알려 시드 밖 입력이 없는지 확인받는다.
2. 백업(혹시를 위해) — DB 와 사진 볼륨을 **둘 다** 떠 둔다(사진 경로는 DB 에, 파일은 볼륨에 있다):
   ```bash
   podman exec ict-twin-postgres pg_dump -U postgres -d digital_next > backup-$(date +%F).sql
   podman volume export uploads_data > uploads_data-backup-$(date +%F).tar
   ```
3. 컨테이너와 DB 볼륨을 지우고 새로 띄운다 — 시드가 빈 DB 에 관리자·조직·마스터·직할 12국을 넣는다.
   ```bash
   podman rm -f ict-twin-postgres ict-twin-backend ict-twin-frontend
   podman volume rm postgres_data
   podman volume rm uploads_data      # 선택 — 2 단계 tar 를 뜬 뒤에만. 1 단계에서 photo=0 이면 비어 있어야 정상
   ```
   이후 띄우기는 4 절과 같고, 띄운 뒤 **6 절 스모크 체크**를 돈다.
4. 이전에 필요했던 수동 작업(lineSide 백필, slotNames 백필, `backfillJikhalLines/Kit --apply`,
   14열 부품 마이그레이션)은 **모두 불필요**해졌다 — 해당 스크립트는 삭제됐다(옛 7-5 절도 걷었다).
5. `uploads_data` 를 남겨 두면 옛 사진 파일은 새 DB 에 행이 없으므로 고아가 된다(photo=0 이면 없음).
   되돌릴 때는 8 절의 DB 복원과 함께 `podman volume create uploads_data; podman volume import uploads_data uploads_data-backup-*.tar` 로 사진도 되돌린다.
6. **재시드를 한 번 더 할 필요는 없다.** 설비 모델 단순화는 아직 한 번도 배포되지 않았고, 3 단계의 초기화가
   곧 빈 DB 에 대한 첫 시드다 — 직할 코어 상태와 **끝별 용도·비고**(`aPurpose·aNote·bPurpose·bNote`)도 그 시드가
   함께 싣는다. 띄운 뒤 선번장(북춘천S/S)에서 코어의 회선 내역이 보이면 된다.

   `scripts/check-migrations.sh` 는 이번 배포에서 **종료 코드 2** 로 끝난다. 걸리는 것은 둘이고, 둘 다 빈 DB 에서는
   예상된 표시다(막힘이 아니다 — 이 스크립트는 「데이터가 있는 서버」에 대고 위험을 세운다):
   - `20261006000000_init` — 새 기준선이라 `CREATE UNIQUE INDEX` 가 여럿 있다(「UNIQUE 추가 → 중복이 있으면 실패」).
     빈 DB 에는 중복이 있을 수 없다.
   - `20261007000000_core_end_values` — `Core.purpose/note` 를 `aPurpose/aNote` 로 `RENAME COLUMN` 한다.
     빈 DB 에는 옮길 값이 없다(값이 있었더라도 이름만 바뀌어 A 끝 값으로 남는다).

   이 두 줄 **말고 다른 것**이 걸리면 멈추고 본다. 다음 배포부터는 이 예외가 없다(7 절).

## 7. 다음 배포부터 — 데이터가 쌓인 서버에 올리기

**2026-09-02 배포부터 서버에는 현장이 쌓은 진짜 데이터가 있다.** 그 사이에도 개발은 계속되므로,
업데이트는 「데이터를 보존하면서」가 전제다. 볼륨을 비우는 일은 **다시 없다**.
(단, 2026-10 설비 모델 단순화 배포 한 번만 예외 — 위 「2026-10 설비 모델 단순화 배포」 절 참조.)

배포한 커밋마다 태그를 단다 — 서버에 무엇이 올라갔는지가 이걸로만 남는다:

```bash

```

### 7-1. 빌드 머신에서 (배포 전)

```bash
npm run build                      # 타입체크 + 빌드
npm test                           # 전부 통과해야 한다
scripts/check-migrations.sh        # ← 배포 태그 이후 새 마이그레이션의 위험 신호
```

`check-migrations.sh` 가 보는 것은 **데이터가 있을 때만 터지는 것**들이다. 개발 DB 는 대개
비어 있어서 `migrate dev` 가 통과해도 서버에서 실패한다:

| 신호 | 무슨 일이 나는가 |
|---|---|
| `DROP COLUMN` · `DROP TABLE` | 값이 **사라진다**(되돌릴 수 없다) |
| 기본값 없는 `NOT NULL` 추가 | 기존 줄에서 마이그레이션이 **실패**한다 |
| `UNIQUE` 추가 | 이미 중복이 있으면 실패한다 |
| 타입 변경 · enum 값 제거 | 변환/참조가 안 되면 실패한다 |

값이 사라지는 변경은 **세 번에 나눈다**: ① 새 칸 추가 → ② 값을 옮기는 마이그레이션 →
③ 옛 칸 삭제. ①②를 먼저 배포해 돌려 놓고, ③은 다음 배포에 넣는다.

### 7-2. 서버 백업으로 리허설 (위험 신호가 있으면 필수)

이것이 진짜 안전망이다 — **서버의 실제 데이터에 대고** 미리 돌려 본다.

```bash
# 서버에서
podman exec ict-twin-postgres pg_dump -U postgres -d digital_next > backup-$(date +%F).sql
# 빌드 머신으로 내려받은 뒤
scripts/rehearse-migration.sh backup-2026-09-02.sql
```

포트 5433 에 임시 DB 를 띄워 백업을 붓고, **서버가 기동할 때 도는 것과 같은** 마이그레이션과
시드를 돌린 뒤 변전소·랙·설비·광선로·연결·점검/고장·사진 수를 세어 준다. 개발 DB 는 건드리지 않고, 끝나면 지운다.

수가 **줄어들면 배포하지 않는다** — 시드나 마이그레이션이 지운 것이다.

### 7-3. 올리기

바뀐 `.txt` 만 덮어쓰고 `./decode-and-deploy.sh` 를 다시 돌린다. 스크립트가 바뀐 이미지의
컨테이너만 다시 만들고, 볼륨과 `.env` 는 건드리지 않는다.


### 7-4. 시드는 쌓인 데이터를 덮지 않는다

기동할 때마다 도는데도 안전한 이유는 **전부 「없을 때만」** 이기 때문이다:

| 시드 블록 | 가드 |
|---|---|
| admin 계정 | `admin` 이 없을 때만 (비밀번호는 손대지 않는다) |
| 조직(본부·사업소) | 본부가 하나도 없을 때만 |
| 분야 · 랙/설비/케이블 품목 | **없는 키만 만든다** — 있는 것은 관리자가 고친 값이라 안 덮는다 |
| 강원 직할 12국(랙·설비·차단기·광선로·코어·측정·연결) | **변전소가 하나도 없을 때만** |

그래서 **시드에 새 품목(새 키)을 더하면 다음 배포에서 운영 DB 에도 생긴다.** 거꾸로, 이미
들어간 품목을 시드에서 고쳐도 운영에는 반영되지 않는다 — 그때는 화면(품목 관리)에서 고친다.

새 참조 데이터를 시드에 더할 때 이 규칙을 깨지 말 것. 「upsert 로 최신값 유지」는 재시작마다
현장이 고친 값을 되돌린다 — 그렇게 한 번 사고가 났다.

### 7-5. 한 번만 돌리는 것 — 지금은 없다

예전에는 기동 시드가 이미 있는 국에 새 값을 채우지 못해 `backfillJikhalLines.js`·`backfillJikhalKit.js` 를
배포 뒤 손으로 돌렸다. 2026-10 설비 모델 단순화 배포가 DB 를 비우고 새로 시드하므로 **그 스크립트는 삭제됐고
돌릴 것이 없다.** 나중에 이미 있는 국에 값을 채워야 하는 변경이 생기면, 미리보기 기본 · `--apply` 로만 쓰기 ·
빈 칸만 채우기(두 번 돌려도 같다)의 같은 규칙으로 새로 만들고 여기에 적는다.
