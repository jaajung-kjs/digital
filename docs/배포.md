# 사내망 배포 절차

사내망은 **폐쇄망(RHEL 9.4 · podman, compose 없음)** 이고, 인트라넷 업로드 필터가 **`.txt` 만**
통과시킨다. 그래서 이미지를 base64 `.txt` 로 싸서 옮긴다 — 이 문서는 그 순서다.

## 이번 배포의 성격

전면 재구축을 지나 **옛 DB 와 스키마가 이어지지 않는다.** 그래서 이번 한 번만 볼륨을 비운다.
그 뒤의 배포는 볼륨을 보존한다(바뀐 `.txt` 만 다시 올리면 된다).

컨테이너가 뜰 때 **`migrate deploy` → `seed` → 서버** 가 자동으로 돈다.

| 시드가 채우는 것 | 시드가 채우지 않는 것 |
|---|---|
| `admin` 계정 · 조직(본부 15 · 사업소 59) | **변전소** — 트리에서 만든다 |
| 분류 4 · 장비 품목 23(포트 42) · 설비 품목 6 | **기준정보**(노임·제비율) — 화면에서 올린다 |
| 케이블 그룹 5 · 케이블 종류 17 | |

## 1. 빌드 머신에서 (인터넷 되는 곳)

```bash
git pull                       # 배포할 커밋인지 확인
npm run build                  # 타입체크 + 빌드가 통과하는지 먼저
scripts/build-prod-images.sh   # linux/amd64 로 빌드 → dist-deploy/*.txt 5개
```

나오는 것: `postgres.txt` · `backend.txt` · `frontend.txt` · `env.txt` · `deploy.txt`
(합계 수백 MB — 인트라넷 업로드 한도를 넘으면 `backend.txt` 만 나눠 올리는 식으로 쪼갠다.)

**로컬에서 먼저 검증**하는 것을 권한다. 개발 스택과 이름·볼륨이 겹치지 않는 오버라이드가 있다:

```bash
docker compose -f docker-compose.yml -f docker-compose.verify.yml build
docker compose -f docker-compose.yml -f docker-compose.verify.yml up -d
open http://twin.local:8080          # /etc/hosts 에 `127.0.0.1 twin.local`
docker compose -f docker-compose.yml -f docker-compose.verify.yml down -v
```

`localhost` 로 검증하면 안 된다 — HSTS·CSP·CORS·**보안 컨텍스트**가 운영과 달라 헛검증이 된다.
실제로 이 검증에서만 드러난 배포 차단 버그가 있었다(평문 주소에서 `crypto.randomUUID` 없음).

## 2. 서버로 옮기고 첫 실행

```bash
# 다섯 개 .txt 를 한 디렉터리에 둔 뒤
base64 -d deploy.txt > decode-and-deploy.sh
chmod +x decode-and-deploy.sh
./decode-and-deploy.sh          # 첫 실행: .env 를 만들고 멈춘다

vi .env
#   DB_PASSWORD / JWT_ACCESS_SECRET / JWT_REFRESH_SECRET  ← openssl rand -hex 32
#   CORS_ORIGIN=http://<브라우저에 치는 주소>:8080          ← 포트까지 정확히
#   DB_NAME=digital_next   FRONTEND_PORT=8080             ← 그대로 둔다
```

## 3. 이번 한 번 — 옛 볼륨 비우기

```bash
podman rm -f ict-twin-postgres ict-twin-backend 2>/dev/null || true
podman volume rm postgres_data uploads_data 2>/dev/null || true
```

사진 파일은 `uploads_data` 에 있고 그 **경로는 DB 에 있다** — 한쪽만 지우면 깨진 사진이 남는다.
지우기 전에 되돌릴 길을 만들어 둔다:

```bash
podman exec ict-twin-postgres pg_dump -U postgres -d digital_next > backup-$(date +%F).sql
```

## 4. 띄우기

```bash
./decode-and-deploy.sh
podman ps
podman logs --tail=30 ict-twin-backend
```

아래 세 줄이 보이면 성공이다:

```
[seed:next] admin user created
[seed:next] org created — 본부 15, 사업소 59
{"event":"server.start","port":3000,"env":"production"}
```

## 5. 사람이 넣는 것

1. `http://<주소>:8080` 접속 → `admin` / `admin123` → **비밀번호를 바로 바꾼다**
2. 「기준정보」 → 노임단가(hwp) · 제비율(xlsx) 업로드
3. 조직 트리에서 본부 › 사업소에 손을 올리고 `＋` → **변전소** 만들기
4. 없는 전력지사도 같은 방법으로 더한다(시드는 한전 공식 목록의 전력지사만 담았다)

## 6. 스모크 체크 (5분)

- 로그인 → 조직 트리에 본부 15개
- 변전소 하나 만들기 → 평면도 → 「층 추가」 → 「배치」로 설비 하나 놓기 → **저장**
- 현황 · 선번장 · 계통 탭이 각각 뜨는지
- 기준정보에 직종 노임이 보이는지
- 브라우저 콘솔에 빨간 오류가 없는지

## 7. 다음 배포부터 (데이터 보존)

바뀐 `.txt` 만 덮어쓰고 `./decode-and-deploy.sh` 를 다시 돌린다. 스크립트가 바뀐 이미지의
컨테이너만 다시 만들고, 볼륨과 `.env` 는 건드리지 않는다. `migrate deploy` 는 새 마이그레이션만
적용하고 시드는 **없는 것만 만든다**(현장이 고친 조직·품목은 원복되지 않는다).

## 8. 되돌리기

```bash
podman rm -f ict-twin-postgres ict-twin-backend ict-twin-frontend
podman volume rm postgres_data
podman volume create postgres_data
# 3단계 백업(backup-*.sql) 복원 후 이전 이미지 .txt 로 다시 배포
```
