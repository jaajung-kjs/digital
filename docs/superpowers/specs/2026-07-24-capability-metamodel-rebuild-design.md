# Capability 메타모델 재구축 설계 (대규모 리팩토링)

날짜: 2026-07-24
상태: 설계 승인 대기

## 1. 배경과 목표

### 문제 진단

현 시스템은 현황관리에 초점을 맞춰 시작되어, 자산 "타입"이 데이터가 아니라 코드다:

1. `AssetRole` enum(`rack|ofd|panel|slot|feeder|standalone|device`)이 Prisma 스키마 + TS union에 고정 — 새 역할 추가 = 마이그레이션 + 배포.
2. 역할의 의미(컨테이너 여부, 자식 타입, 방향성, 상세패널, 배치 가능 여부)가 백엔드 8개 + 프론트 5개 파일의 `if (role === ...)` 분기에 분산.
3. 컨테이너-자식 관계 1:1 하드코딩: rack→device(12슬롯 고정), ofd→slot, panel→feeder.
4. 추적(trace)이 역할별 특수 로직이며 백/프론트에 복제됨.
5. 선번장(`role==='ofd'`)·계통(`role==='panel'`) 등 파생 뷰가 역할에 직접 결합 — 새 타입은 기존 뷰에 편입 불가.

관리자가 카탈로그에서 새 타입을 만들어도 `role='device'`로 강제되어 "이름만 다른 회색 사각형"이 된다. 과거 리팩토링(A1+ 데이터스코프, SSOT 워킹카피, data-driven 필드, type-agnostic 워크벤치)은 주변부(상태관리·저장경로·UI)를 정리했을 뿐 role-enum 도메인 모델 자체는 교체된 적이 없다 — "첫 출발이 꼬였다"는 느낌의 정체.

### 목표

기존 기능 전체(현황·평면도·선번장·계통·설계서 산출·이력·케이블 추적)를 유지한 채, **관리자가 UI에서 100% 새 자산 타입을 정의**할 수 있는 표준 자산관리 + 현황관리 시스템으로 재구축한다. 개발자 개입 없이 "신형 장비: 랙 2슬롯 점유, 광 포트 16개, 전원 IN 2개"를 정의하면 배치·연결·추적·선번장·설계서에 즉시 참여한다.

### 확정된 방향 (사용자 결정)

| 결정 | 선택 |
|---|---|
| 타입 정의 주체 | 관리자가 UI에서 100% (개발자 개입 0) |
| 재구축 범위 | 신규 도메인 코어 + 검증된 인프라(워킹카피·캔버스·UI 컴포넌트) 재사용 |
| 파생 뷰 일반화 | 코드 뷰 유지 + capability 질의 결합 |
| UX | 거동 동일 + 개선 허용 |
| 메타모델 | A안: Capability 조합 (NetBox류 DCIM 표준의 변전소 특화) |
| 기존 DB | 삭제 허용 — 신규 스키마로 리셋 |

## 2. 도메인 모델

### 원칙

**엔진(capability 종류)은 코드, 어떤 타입이 어떤 capability를 어떤 파라미터로 갖는지는 100% 데이터.** EAV식 완전 범용화는 하지 않는다 — 불변식이 강한 고정 스키마 위에 타입 정의만 데이터화.

### 계층 구조 (유지)

`본부 → 지사 → 변전소 → 층(평면도)`. 이력·점검·사진 레코드는 타입 무관 제네릭 유지.

### 카탈로그 (타입 정의 = 데이터)

```
AssetCategory  분류 (관리자 편집)
AssetType
 ├─ 기본: 이름, 분류, 정렬, 활성 여부
 ├─ 배치 명세: 평면도 배치 가능 여부 + 기본 크기
 ├─ 공량 규칙: 노무유형, 신설/철거/이설 공량
 ├─ 커스텀 필드 정의: [{key, 라벨, 자료형, 단위}]
 ├─ ContainerSpec[]: 슬롯 수(자유형 null), span 허용, 수용 조건(분류/타입)
 ├─ PortTemplate[]: 그룹명, 수량(인스턴스 오버라이드 가능 — 예: 12C/24C 광슬롯), 방향(IN/OUT/양방향), 매체, 이름 패턴
 └─ InternalLinkRule[]: fromGroup→toGroup, 매핑(인덱스 패스스루/전체)
```

기존 7개 role의 데이터 표현:

| 기존 role | 새 모델 표현 |
|---|---|
| rack | 배치 + ContainerSpec(슬롯 12, span 허용, 통신장비류 수용) |
| ofd | 배치 + ContainerSpec(자유형, 광슬롯 타입 수용) |
| slot(광슬롯) | PortTemplate(A측 코어 1~N, B측 코어 1~N) + 인덱스 패스스루 |
| panel(분전반) | 배치 + ContainerSpec(피더 타입 수용) |
| feeder | PortTemplate(IN 1, OUT 1) + 패스스루 |
| device/standalone | 배치 명세 + 포트 템플릿만 |

"12슬롯 고정", "rack→device만", "feeder만 방향성" 등의 제약이 전부 파라미터가 된다.

### 인스턴스

```
Asset   typeId + 이름 + 위치 + 커스텀 필드값 + 상태
         위치 = 평면도(floorId, x, y, w, h) 또는
                컨테이너(parentAssetId, containerSpec, slotIndex, span)
Port    자산 생성 시 포트 템플릿에서 인스턴스화 (이름 오버라이드 가능)
Cable   포트 ↔ 포트 + 케이블 종류(데이터) + 경로점 + 스펙
```

케이블은 자산이 아니라 **포트**에 물린다. 현행 `sourceRole/number` 특수 컬럼 폐지. OFD 코어 선택·피더 IN 슬롯이 "포트 선택" 단일 UX로 통일.

### 추적 엔진

그래프 = 포트 노드 + 케이블 엣지 + InternalLinkRule에서 파생된 내부 엣지. 추적은 범용 그래프 탐색 하나. 역할 분기 0. 공유 패키지로 백/프론트가 같은 엔진 사용.

### 검증기

"이 자산을 이 컨테이너에 넣어도 되는가"(수용 조건·슬롯 충돌), "이 케이블을 이 포트에 물려도 되는가"(포트 점유·매체 일치)를 타입 명세를 읽어 판정하는 범용 검증기 하나가 기존 하드코딩 검증 전부를 대체.

## 3. 시스템 구조

### 백엔드

스택 유지(Express + Prisma + PostgreSQL), 스키마 신규.

```
routes/controllers   HTTP 껍데기 (인증·파싱)
domain/              순수 도메인 코어 — DB·HTTP 무관, 프론트와 공유
  ├─ validation      capability 기반 범용 검증기
  ├─ trace           범용 그래프 추적
  └─ report          before/after diff + 공량 계산
services/            트랜잭션 조립 (커밋, 카탈로그 커밋, 벌크 로드)
```

API 표면은 현행 패턴 유지: 카탈로그 CRUD+커밋, workingcopy 벌크 로드, commit(원자+OCC), trace, report-preview. payload만 신모델.

### 프론트엔드

**그대로 이식:** 워킹카피 스토어(base ⊕ overlay, 컬렉션 레지스트리, 단일 커밋, undo/redo, OCC), 캔버스 렌더러·히트테스트·배경도면, UI 컴포넌트 시스템 + CONVENTIONS + 디자인 토큰, SSOT 가드레일 테스트 체계.

**신모델 재작성:**
- 상세패널: `ROLE_TO_PANEL` → capability 렌더링 (ContainerSpec 있으면 슬롯 그리드 섹션, PortTemplate 있으면 포트 섹션 자동 표시)
- 배치 도구바: 하드코딩 배열 → "배치 가능 타입" 질의
- 케이블 연결: 종류우선 FSM·우측패널 피커 UX 유지, 대상을 포트로 통일
- 관리자 타입 정의 화면(신규): 기본정보 + 슬롯 명세 + 포트 템플릿 + 통과 규칙 + 공량을 한 화면에서. 자산마스터 편집형 테이블 UX 확장.

### 파생 뷰 결합

- 선번장: "광 매체 포트를 가진 자식을 수용하는 컨테이너" 질의. 코어별 행·대국 표시 UX 동일.
- 계통: "전원 매체 IN/OUT 포트 구성을 가진 타입" 질의. 차단기 번호·상태는 커스텀 필드.
- 설계서: before/after diff 구조 유지 — 공량 규칙이 타입 데이터에 있어 오히려 단순화.

### 시드 = 모델 증명

기존 31개 타입을 새 메타모델의 순수 데이터로 재표현한 카탈로그를 시드로 작성 — 기존 도메인 전체가 데이터로 기술됨을 증명. 참조데이터 upsert 멱등 원칙 준수(운영 데이터는 첫 배포에만).

## 4. 전환 전략

같은 레포에서 신규 스키마로 리셋 후 기능별 수직 재건. 각 단계가 동작하는 시스템 유지, **단계마다 main 머지** (브랜치 병렬 진행 금지 — 과거 실패 패턴의 해독제):

1. 신규 스키마 + 도메인 코어(검증·추적) + 시드 — 단위테스트로 코어 검증
2. 워킹카피/커밋 배선 + 현황 뷰
3. 평면도 (배치·캔버스)
4. 포트·케이블·추적
5. 선번장 → 계통 → 설계서
6. 관리자 타입 정의 화면
7. 구모델 코드 제거 + 가드레일 확장

## 5. 검증 계획

- 도메인 코어: 수용 검증·슬롯 충돌·추적 순수 함수 단위테스트 (기존 7 role 재현 시나리오 포함)
- 가드레일: "타입 이름/역할 문자열 분기 금지" 정적 검사 테스트
- E2E: 타입 정의 → 배치 → 연결 → 추적 → 선번장 → 설계서 한 줄기
- 각 단계 완료 시 dev 서버 브라우저 검증 후 머지 ("검증 예정" 상태로 남기지 않음)

## 6. 명시적 비목표

- EAV/완전 범용 그래프 모델 (데이터 품질·UX·성능 리스크로 기각)
- 뷰 자체의 설정 기반 범용 엔진화 (선번장·계통은 코드 뷰 유지)
- 기존 DB 데이터 마이그레이션 (DB 리셋 승인됨)
- feat/asset-master-workbench 브랜치 이어받기 (설계 사상은 흡수, 코드는 신규)
