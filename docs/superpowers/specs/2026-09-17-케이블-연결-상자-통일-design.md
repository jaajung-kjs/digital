# 케이블 연결을 상자 하나로 — `ConnectCableModal`

> 진입점이 하는 일은 **출발을 정하는 것** 하나다. 그 뒤는 어디서 왔든 똑같다.

## 왜

케이블을 잇는 **쓰기**는 이미 한 곳이다(`cableActions.ts` 의 `connectCable`). `aPortId`/`bPortId`
를 쓰는 자리를 전수로 훑으면 거기와 설비 품목의 내부 배선(`placeAssembly.ts:117`, 사람 손짓이
아니다) 둘뿐이다. **제각각인 것은 쓰기가 아니라 「어떻게 잇게 하느냐」다.**

### 단계 번호가 뒤로 간다

`FloorPlanView.tsx:496-513` 이 단계를 상태 조합에서 유도하는데, 그 조합이 왕복한다.

| 사용자가 하는 일 | 상태 | 화면 |
| --- | --- | --- |
| 출발 설비 클릭 | `picker` 열림 | **2/3** 오른쪽 판에서 포트를 고르세요 |
| 출발 포트 고름 | `firstPortId` 섬 | **3/3** 경로를 그리고 반대쪽 설비를 클릭 |
| 도착 설비 클릭 | `picker` **다시 열림** | **2/3** ← 번호가 뒤로 간다 |
| 도착 포트 고름 | `CABLE_STAGED` | **1/3** 이을 설비를 클릭하세요 |

실제 걸음은 다섯인데 셋으로 세고 있어서 `2/3` 가 두 번 나온다. 그리고 `CABLE_STAGED`
(`cableTool.ts:114`)가 `firstPortId` 만 비우고 `armed` 를 유지하므로 — 연속 연결을 위한
설계다 — **이었다는 말 없이** `1/3` 로 돌아간다. 방금 완성한 일이 실패한 것처럼 보인다.

### 종류를 고를 자리가 진입점마다 다르다

도면에서 시작하면 도구바에서 **먼저** 고른다. 포트에서 시작하면 고를 기회가 없고,
`FloorPlanView.tsx:479-485` 가 대신 집는다.

```
if (selectedGroupKey !== port.medium) {
  const first = cableGroups.find(g => g.key === port.medium)?.categories[0];
  if (first) cableDispatch({ type: 'SET_CATEGORY', categoryId: first.id });
}
```

그 매체 그룹의 **첫 품목**을 말없이 집는다. 광 포트면 「OPGW(광복합가공지선)」이 되는데,
정작 이으려던 것이 「광점퍼코드」여도 그렇다. 매체가 이미 맞으면 **직전에 쓰던 품목**을
조용히 재사용한다. 둘 다 화면에 아무 말이 없다 — 고친 적 없는 값이 저장된다.

### 표에서는 아예 못 잇는다

선번장·계통의 `PeerCell` 은 `onSelect(assetId, portId)` 로 **선택만 옮긴다**. 빈 칸은
`PeerCell.tsx:54` 에서 눌리지 않는 글자로 끝난다 — 심선 24개를 잇는 자리에서 잇는 길이 없다.

## 무엇을 만드나

### ① 진입점은 **출발을 정하는 방법**일 뿐이다

출발이 정해지는 순간 상자가 뜬다.

| 진입점 | 출발을 정하는 방법 | 지금 |
| --- | --- | --- |
| 평면도 | 「케이블」 무장 → 설비 클릭 → 포트 고르기 | 있음 |
| 포트 탭 | 빈 포트 클릭 | 있음(평면도로 끌려간 뒤 3/3 상태) |
| 선번장 빈 칸 | 그 심선의 자국/대국 칸 클릭 | **새로 생김** |
| 계통 빈 부하 칸 | 그 회로의 부하 칸 클릭 | **새로 생김** |

### ② 상자 — 세 칸이 **동시에** 보인다

```
┌─ 케이블 연결 ─────────────────────────────┐
│ 출발   OFD · 슬롯 1 · 광 1        [바꾸기]  │
│ 도착   [도면에서] [목록에서] [다른 국에서]     │
│        ─ 아직 안 골랐습니다 ─               │
│ 종류   광점퍼코드  ▾   (광 품목만)          │
├───────────────────────────────────────────┤
│ □ 이어서 또 잇기            [취소] [잇기]    │
└───────────────────────────────────────────┘
```

- **단계 번호가 없다.** 남은 것이 무엇인지는 빈 칸이 말한다. `1/3`~`3/3` 문구와 `cableStep`
  (`FloorPlanView.tsx:496`)은 사라진다.
- **도착 고르는 길 셋은 탭이다.** 진입점은 **어느 탭이 기본인지**만 정한다 — 도면에서 열면
  「도면에서」, 표·포트 탭에서 열면 「목록에서」. 고른 결과는 셋 다 같은 칸에 들어간다.
- **「도면에서」를 고를 때만 경로를 그린다.** 상자가 비켜서고 도면을 누른다(지금의 경로 그리기
  그대로). 다른 길로 고르면 직선이고, 경로는 나중에 도면에서 점을 붙인다(기존 경로점 편집).
- **「잇기」는 세 칸이 다 차야 켜진다.** 못 잇는 까닭은 그 칸 밑에 적는다.
- **이으면 상자가 닫히며 「이었습니다」.** 「이어서 또 잇기」를 켜 두면 **출발만 비우고** 다시
  뜬다 — 지금의 연속 연결을 말이 되게 옮긴 것이다.

### ③ 도착 후보와 종류 목록을 거르는 규칙 — **사실이지 짐작이 아니다**

- **도착 후보**: `portKind(출발매체).connectsTo` 가 정한 매체의 포트 중 자리가 남은 것.
  **「같은 매체」가 아니다** — 어휘가 짝을 정한다(`validation/connection.ts:38-41`). 어휘에
  없는 매체는 예전 규칙(같은 매체끼리)으로 둔다. 지금 `connectableAssetIds`
  (`cableTool.ts`)가 `p.medium === mediumKey` 로 거르는데, 그것은 **케이블 품목의 매체**를
  기준으로 한 것이라 출발 포트 기준과 다르다. 새 흐름에서는 출발 포트가 기준이다.
- **종류 목록**: `cableMedium !== undefined && a.medium !== cableMedium` 이므로
  (`validation/connection.ts:42`) 케이블의 매체는 **출발 포트의 매체와 같아야 한다**. 그러니
  종류 목록을 출발 매체의 그룹으로 거르는 것은 규칙이 이미 말하는 사실이다.

### ④ 걷어내는 휴리스틱 셋

| 지금 | 뒤 |
| --- | --- |
| `FloorPlanView.tsx:483` 매체 그룹의 **첫 품목을 말없이** 집는다 | 종류 칸이 눈에 보이고, **직전에 그 매체에 쓴 것**이 고른 채로 들어간다. 처음이면 비어 있고 「잇기」가 꺼져 있다 |
| 매체가 맞으면 **직전 품목을 조용히** 재사용 | 같은 값이지만 **화면이 무엇을 골랐는지 말한다** |
| 이은 뒤 말없이 `1/3` 로 리셋 | 「이었습니다」 + 「이어서 또 잇기」 |

**직전에 쓴 것**은 매체별로 기억한다(`Record<medium, categoryId>`). 화면이 그 값을 고른 채로
보여 주므로 숨은 값이 아니다 — 고른 것이 무엇인지 늘 읽힌다.

### ⑤ 코드에서 바뀌는 것

| 무엇 | 어떻게 |
| --- | --- |
| `cableActions.ts` `connectCable` | **그대로.** 쓰기 단일 지점이고 이미 옳다 |
| `cableTool.ts` `cableToolReducer` | **도면에서 끝점 고르기**만 남긴다(`ARM`·`OPEN_PICKER`·`CONFIRM_FIRST_ENDPOINT`·경로·케이블 선택). `categoryId`·`remoteModalOpen`·`remoteError` 는 상자로 옮긴다 |
| `RemoteEndpointModal` | 상자 안의 **한 탭**이 된다(별도 모달 아님) |
| `FloorPlanView.tsx:496-513` `cableStep` | **사라진다** |
| `FloorPlanView.tsx:475-488` `startConnectionRef` | 종류를 집는 세 줄이 빠지고, **상자를 여는 일**만 남는다 |
| `CablePickRequest` (우측 패널 포트 피커) | **그대로** — 도면에서 포트를 고르는 장치로 계속 쓴다 |
| `cableTool.ts` `connectableAssetIds` | 거르는 기준이 **케이블 품목의 매체 → 출발 포트의 `connectsTo`** 로 바뀐다(종류를 나중에 고르므로 그때는 케이블 매체가 없다). 인자 `mediumKey` 가 `fromPortMedium` 이 된다 |
| `PeerCell` | 빈 칸이 **눌린다**. 누르면 그 심선/회로의 포트를 출발로 삼아 상자를 연다 |

**상자는 `V2WorkspacePage` 가 쥔다.** 네 진입점이 모두 그 페이지 아래에 있고(평면도·상세
패널·선번장·계통), 상자가 어느 한 판에 들어 있으면 그 판을 떠날 때 함께 사라진다. 지금
`cableStartPortId`·`cablePick` 이 그 페이지에 사는 것과 같은 까닭이다 — 둘은 상자가 생기면
**하나로 합쳐진다**(「출발이 정해졌다」는 사실 하나).

### ⑥ 덤 — 케이블 값 편집 세 벌을 하나로

「케이블의 `specParams` 한 칸을 고친다」가 같은 글로 세 곳에 복사돼 있다.

| 파일 | 이름 |
| --- | --- |
| `FiberRegisterView.tsx:40~85` | `CableFieldInput` |
| `PowerRegisterView.tsx:44~85` | `CableFieldInput` |
| `SelectedPortCard.tsx:61~82` | `CableValueControl` |

셋 다 같은 일을 한다: 숫자면 `Number()`, 빈 값은 `null`, `NaN` 이면 무시, 무변경이면 무시,
스토어에서 케이블을 다시 읽어 `specParams` 를 합쳐 `stageCableUpdate`. `CableValueField`
하나로 합친다. 같은 케이블의 같은 칸인데 검증이 세 벌인 상태다.

## 손대지 않는 것

- **`connectCable` 의 검증**(`validateConnection`) — 규칙은 core 의 것이고 이미 한 곳이다
- **설비 품목의 내부 배선**(`placeAssembly.ts` → `stageAssemblyCables`) — 사람 손짓이 아니라
  선언에서 펴지는 것이고, 이미 저장 때 `validateAssembly` 를 통과했다
- **경로점 편집**(도면에서 선을 끌어 꺾기) — 그대로
- **케이블 삭제**(`deleteCableWithConfirm`) — 이미 한 곳이다

## 어떻게 확인하나

- **`cableToolReducer` 시험**(`__tests__/cableTool.test.ts`)이 통과한다. 상자로 옮겨 간 동작
  (`SET_CATEGORY`·원격)은 시험도 함께 옮긴다.
- **새 시험** — 「진입점이 달라도 상자의 상태가 같다」를 못 박는다: 도면에서 연 것과 포트 탭에서
  연 것이 같은 `from`·같은 종류 목록·같은 도착 후보를 갖는다.
- **새 시험** — 종류를 안 고르면 「잇기」가 꺼져 있다(휴리스틱이 사라졌다는 증거).
- **`npm run build`** 로 타입체크 + 빌드, 프론트·core 시험 전부.
- **눈으로** — 네 진입점에서 차례로 열어 **같은 상자**가 뜨는지, 이은 뒤 「이었습니다」가 뜨는지,
  「이어서 또 잇기」가 출발만 비우는지.

## 쪼갤 수 있는 것

범위를 줄이려면 아래 둘은 떼어낼 수 있다 — 통일 자체는 그것 없이도 선다.

1. **선번장·계통 빈 칸 진입점**(①의 아래 두 줄, ⑤의 `PeerCell`) — 새 기능이다
2. **⑥ 케이블 값 편집 합치기** — 연결 흐름과 별개의 중복이다
