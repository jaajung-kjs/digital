# 설비 현황 네 탭 골격 통일 — `ViewCard`

> 회색 바탕 위에 흰 카드가 뜬다. 그 카드의 머리 띠가 곧 도구바다.

## 왜

설비 현황 안의 네 탭(현황·평면도·선번장·계통)이 저마다 다른 껍데기를 그리고 있다.
같은 일(도구바 한 줄 + 본문)을 네 곳이 각자 구현해서, 좌측 기준선·줄 높이·검색 자리가
전부 어긋났다.

### 실측 — 좌측 기준선이 네 값이다

| 줄 | 좌측 시작 | 근거 |
| --- | --- | --- |
| 머리줄 `설비 현황` | 16px | `PageHeader.tsx:25` `px-4` |
| 뷰 탭 줄 | 16px | `V2WorkspacePage.tsx:362` `px-4` |
| 현황 — 검색 줄 | 16px | `V2WorkspacePage.tsx:415` `p-4` (**페이지가 준다**) |
| 평면도 — 층 탭 줄 | **0px** | `FloorPlanView.tsx:1642` |
| 평면도 — 도구바 | **8px** | `FloorPlanView.tsx:1664` `px-2` |
| 선번장·계통 — 도구바 | **12px** | `RegisterLayout.tsx:108` `px-3` |
| 선번장·계통 — 표 본문 | 16px | `RegisterLayout.tsx:136` `p-4` |

뷰 탭 줄의 `px-4` 자체는 머리줄 제목과 맞아서 옳다. 어색해 보이는 것은 **바로 아래 줄이
0·8·12px 에서 시작**하기 때문이다 — 평면도가 가장 나쁘다(탭 줄 둘이 16px 어긋난 채 겹친다).

### 같은 사각 탭이 세 위계에 선다 — 아래가 더 크게

| 탭 | 줄 높이 | 바탕 |
| --- | --- | --- |
| 뷰 탭 (1차) | 32px 고정 (`h-8 items-end`) | `surface-2` |
| 평면도 층 탭 (2차) | 미지정 ≈30px | 흰색 |
| 계통 갈래 탭 `전체·교류·직류` (2차) | **≈46px** (탭 30 + `py-2` 16) | 흰색 |

전부 같은 `Tabs` 컴포넌트다. 하위가 상위보다 14px 더 높아서 위계가 읽히지 않는다.

### 검색이 세 어법

- **현황** — 띠 없이 본문 여백 안에 떠 있고, 아래에 칩 줄이 따라옴. 이 탭에만 `max-w-6xl`
  제약이 있음 (`StatusOverview.tsx:152,165`)
- **선번장** — 회색 띠 안, `Select(w-64)` 뒤
- **계통** — 회색 띠 안, 탭 뒤
- **평면도** — 없음

`TableSearch` 로 폭(256px)은 같은데 시작 x 가 매번 달라, 탭을 옮길 때마다 눈이 검색을 새로 찾는다.

### 근본 원인 — 껍데기의 주인이 셋이다

`RegisterLayout` 은 선번장·계통 **둘만** 덮는다. 현황의 여백은 **페이지**가 주고
(`V2WorkspacePage.tsx:415`, 게다가 자식이 하나뿐인데 `gap-3` 이라 죽은 값), 평면도는
**자기가** 그린다.

### 관리 화면과의 진짜 차이

페이지 바탕은 `--bg: #EDEFF1` 회색이다(`index.css:21`). 관리 화면이 「카드가 뜬다」로
보이는 것은 이 회색 위에 흰 카드가 얹히기 때문인데, **설비 현황의 현황·선번장·계통도
이미 같다** — `p-4` 안에 흰 `TableCard`, 그 뒤는 같은 회색.

그러니 「설비 현황만 다르다」의 실체는 둘뿐이다.

| 차이 | 설비 현황 | 관리 화면 |
| --- | --- | --- |
| 우측 패널 | `border-l border-line bg-surface` — 가장자리에 붙은 **흰 벽**, 여백 0 | `aside w-96 gap-3 overflow-y-auto` — 회색 위에 **뜨는 카드** (`CableCatalogPanel.tsx:403`) |
| 평면도 | 여백 0, 캔버스가 가장자리까지 | (해당 없음) |

설비 관리 화면이 깔끔한 것은 사이드패널이 없어서가 아니다 — 그것도 `w-96` 사이드패널이다
(`기본정보`·`공량`). 벽이 아니라 카드로 떠서 왼쪽 `구성` 카드와 **같은 층위**로 읽힐 뿐이다.

관리 화면끼리도 어긋난 곳이 있다: 기준정보는 검색이 **카드 안**(머리 띠 아래)인데,
케이블 관리는 「종류 4 … `+ 종류 추가`」가 **카드 밖** 회색 위에 맨줄로 떠 있다
(`CableCatalogPanel.tsx:329-338`).

### ① 골격

```
AppBar 46 ─────────────────────────────────────────  (가장자리까지)
MenuBar 34 ────────────────────────────────────────  (가장자리까지)
┌트리 w-64┬ PageHeader 38 ──────────────────────────  (가장자리까지)
│border-r │ 뷰 탭 줄 32 ────────────────────────────  (가장자리까지)
│         │▒▒▒▒▒▒ gap-3 p-4 · 회색 #EDEFF1 ▒▒▒▒▒▒▒▒▒
│         │▒ ┌─ 판 ViewCard ─┐ ┌─ 상세 ViewCard ─┐ ▒
│         │▒ └───────────────┘ └─────────────────┘ ▒
└─────────┴──────────────────────────────────────────
```

**벽은 화면 구조에만**(트리 `border-r`, 머리줄, 뷰 탭 줄), **카드는 내용에만**.
지금 설비 현황의 우측 패널만 이 규칙을 어긴다.

본문 컨테이너는 관리 화면과 **같은 한 줄**이다 — `flex min-h-0 flex-1 gap-3 p-4`
(`CableCatalogPanel.tsx:325`).

### ② `ViewCard` — 좌우가 같은 컴포넌트

```tsx
<ViewCard
  title?    // 머리 띠 왼쪽 (text-sm font-semibold text-content) — 상세 패널이 쓴다
  tools?    // 머리 띠 왼쪽 — 거르개·범위 고르개·도구
  actions?  // 머리 띠 오른쪽 끝 — 검색 또는 버튼
  status?   // 회색 바닥 띠 — 평면도만
  body="scroll | fill | bleed"
>
```

머리 띠 규격: `surface-2` · **h-8** · `px-3` · `border-b border-line-strong`.
`DetailCardHeader`(`DetailCard.tsx:88`)와 **같은 면**이라 §3.2 「한 절 = 한 카드」 어법 안에 있다.
높이가 28px 이 아니라 32px 인 것은 머리 띠에 `size="sm"` 컨트롤(24px, `controlSize.ts`)이
들어가기 때문이다.

- **왼쪽 첫 칸은 늘 「범위를 고르는 것」** — 거르개·범위 고르개·갈래
- **오른쪽 끝은 늘 검색** — 네 탭에서 x 좌표가 같다. 검색이 없는 탭은 자리를 비운다.

| `body` | 스크롤 주인 | 안쪽 여백 | 쓰는 곳 |
| --- | --- | --- | --- |
| `scroll` | 카드 (안쪽 래퍼에 `p-4`) | 16px | 선번장·계통 |
| `fill` | 자식 `TableCard fill` | **0** | 현황 |
| `bleed` | 없음 | **0** | 평면도 |

세 값은 §1.7-b 의 두 가지 스크롤 소유권 + 캔버스를 그대로 옮긴 것이다. 고정 머리글이 있는
스크롤 상자에 여백을 직접 주지 않는다는 규칙은 `scroll` 이 안쪽 래퍼에 여백을 주는 것으로 지킨다.

`scroll` 만 안쪽 여백이 있는 까닭: 선번장·계통은 카드 **안에 묶음 표를 여러 장** 쌓는다
(`RegisterLayout` 의 `sections`). 그 장들이 바깥 카드 테두리에 붙으면 어디서 묶음이 시작되는지
흐려진다. 현황은 표 한 장이 카드를 채우므로 여백이 낭비다.

**`fill`·`bleed` 의 안쪽 여백이 0인 것이 되돌린 `fcaef075` 와 결정적으로 다른 점이다.**
`DetailCard` 는 줄 아닌 자식에 `px-2.5 py-2` 를 강제하는데(`DetailCard.tsx:45-47`), 그때
캔버스와 표가 테두리 안에서 한 겹 더 들여쓰기 됐다.

### ③ 탭별

| 탭 | 머리 띠 | 본문 | 바닥 띠 |
| --- | --- | --- | --- |
| **현황** | `[설비 7][장비 32][고장 0][미점검 39]` ⟶ 검색 | `fill` · `TableCard fill` | — |
| **평면도** | `[배치][▾OFD] │ [케이블][▾F-CV] [🗑]` ⟶ `⋯`(배경 임포트·제거) | `bleed` · 캔버스 | `(3층)(4층)(+) │ 좌표 │ 스냅 │ 격자 │ 설비 │ 배율` |
| **선번장** | `[▾ OFD]` ⟶ 검색 | `scroll` · 묶음 표 | — |
| **계통** | `[전체│교류│직류]` ⟶ 검색 | `scroll` · 묶음 표 | — |
| **상세 패널** | 이름(조상 경로) ⟶ `[평면도에서 보기][✕]` | 탭 + 내용 | — |

**평면도의 층 탭은 화면 아래로 내린다** — Excel 시트·AutoCAD 배치·Figma 페이지와 같은 자리다.
기존 `StatusBar`(`FloorPlanView.tsx:1937`)의 왼쪽 끝에 붙어 한 줄이 된다. 그러면 위쪽 크롬이
두 줄에서 한 줄로 줄어 탭 줄이 겹치는 문제가 사라지고, 도구바 폭에 검색이 들어갈 여유가 생긴다
(다만 검색 기능 자체는 이번에 만들지 않는다 — 자리만 비워 둔다).

`배경 임포트`·`배경 제거`는 도구바 오른쪽 `⋯`(`OverflowMenu`)로 들어간다 — 관리자만, 드물게
쓰는 것이라 §1.7-h 의 자리다.

**계통의 `전체·교류·직류`는 사각 탭을 벗는다.** 1차 뷰 탭과 같은 모양이면 위계가 안 읽힌다.

## 어떻게 확인하나

- **기존 테스트가 통과한다.** 프론트 497건. 도구바 DOM 을 짚는 테스트가 있으면
  (`FiberRegisterView`·`PowerRegisterView`·`StatusOverview`·`scrollSelectedIntoView`)
  새 구조에 맞춰 고친다 — 단, **무엇을 검사하는지는 바꾸지 않는다**(선택·검색·스크롤 거동).
- **`npm run build`** 로 타입체크 + 빌드 검증.
- **눈으로 확인할 것** — 네 탭을 차례로 눌러 보며:
  - 도구바의 검색(또는 빈 자리)이 **같은 x 좌표**에 있다
  - 탭을 옮겨도 카드 테두리와 회색 여백이 **자리를 바꾸지 않는다**
  - 고정 머리글이 스크롤 중에 붙어 있고 그 아래로 행이 비치지 않는다(§1.7-b)
  - 평면도 캔버스가 카드 안에서 **안쪽 여백 없이** 꽉 찬다
  - 상세 패널을 열고 닫아도 왼쪽 판의 폭이 변하지 않는다(§1.7-e)
### 눈으로 정해야 하는 것 둘

구현 중에 실제 화면을 보고 정한다. 어느 쪽이든 규칙을 CONVENTIONS 에 적는다.

1. **맞닿는 두 회색** — 뷰 탭 줄 바탕(`surface-2` #F4F5F6)과 그 아래 작업면(`--bg` #EDEFF1)이
   붙는다. 얼룩져 보이면 탭 줄을 `--bg` 로 내린다(비활성 탭이 `bg-surface-2/60` 이라 대비는 남는다).
2. **카드 안의 카드** — `scroll` 본문은 흰 바탕인데 그 위에 묶음 표(제 테두리를 가진 카드)가
   쌓인다. 지금은 회색 위라 경계가 또렷하다. 흰 위에서 테두리만으로 부족해 보이면 `scroll`
   본문만 `--bg` 로 깔아 지금 모습을 유지한다.

## 순서

위험이 낮은 것부터. 각 단계가 독립 커밋이다.

1. **`ViewCard` + 선번장·계통** — `RegisterLayout` 을 `ViewCard` 위에 다시 세운다.
   겉보기 변화는 도구바 규격(12px→16px, 40px→32px, 검색이 오른쪽 끝)뿐이라 가장 안전하다.
   `SegmentedControl` 도 여기서 들어온다.
2. **현황** — `FilterChip` 추가, 칩·검색이 한 줄로, 여백 소유권 이동, `max-w-6xl` 제거.
3. **상세 패널 + 페이지 골격** — 벽 → 카드, `gap-3 p-4`, 레일 412px.
4. **평면도** — `FloorPlanView` 가 1990줄이고 층 탭 이동이 이름변경·`⋯` 메뉴·`floorPrompt`
   배선을 건드린다. **반드시 별도 커밋.**
5. **케이블 관리** — 맨줄 → 카드 머리 띠.
6. **CONVENTIONS §3.1** — 「화면의 판 — `ViewCard`」 절을 §3.9(껍데기)와 §3.2(한 절 = 한 카드)
   사이에 쓴다. 되돌린 `fcaef075` 가 적으려던 자리이고, **`fill`·`bleed` 의 안쪽 여백이 0인
   까닭**을 그 절에 남긴다.

## 되돌린 커밋과의 관계

`fcaef075`(→ `55ca35aa` 로 revert)가 같은 문제를 겨눴다. 그때 되돌린 까닭은
「카드로 감싸니 테두리·여백이 낭비」였다. 이번에 다른 점:

1. **판에는 안쪽 여백을 주지 않는다** — `fill`·`bleed` 가 0. `DetailCard` 의 `px-2.5 py-2`
   강제가 캔버스·표를 한 겹 더 들여쓰던 것이 그때의 「여백 낭비」였다.
2. **도구바가 카드의 머리 띠가 된다** — 카드가 줄을 하나 더 얹는 것이 아니라, 이미 있던
   도구바가 카드의 일부로 들어간다. 세로 크롬이 늘지 않는다.
3. **한 커밋에 다 가지 않는다** — 위 여섯 단계가 각각 독립 커밋이고, 평면도는 따로 간다.
